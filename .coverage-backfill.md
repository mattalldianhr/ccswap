# Test-coverage backfill (ccswap)

You are adding tests to one under-tested module of ccswap per run. Small, focused,
genuinely useful tests — not coverage theater.

## Scope: one module per run

Do not attempt the whole codebase. Pick **one** module, test it well, stop.

Selection, in order:
1. Run coverage: `uv run pytest --cov=src --cov-report=term-missing -q` (add `pytest-cov`
   to the dev deps if missing — that counts as part of the work).
2. Choose the module with the **worst ratio of uncovered lines to complexity** that you
   can meaningfully test. Prefer logic-heavy modules (`jobs.py`, `jobs_engine.py`,
   `capacity.py`) over TUI screens, which are expensive to test and brittle.
3. If a previous run left `COVERAGE-BACKFILL.md`, read it and pick a module that has not
   been done yet.

## Rules

- **Never weaken an existing test** to make something pass. If a test fails, the test is
  telling you something — investigate, and report it rather than editing it away.
- **Test behavior, not implementation.** Assert what the function does, not how. Tests
  coupled to internals break on every refactor and are worse than no tests.
- **No mocking the thing under test.** Mock the subscription API and the clock; do not
  mock the scheduler to test the scheduler.
- Match the conventions already in `tests/` — fixtures, naming, structure. Read two or
  three neighboring test files first.
- Do not touch `src/` except to fix a genuine bug the new tests expose. If you find one,
  fix it only if the fix is small and obviously correct; otherwise report it.
- The full suite must pass. `uv run pytest -q` green before you commit, no exceptions.

## Value over percentage

A test asserting `capacity()` returns a float is worthless. A test proving the scheduler
refuses to start a job when the forecast would breach a reserve is worth ten of those.
Aim at the second kind: edge cases, boundary conditions, error paths, the logic that
would quietly corrupt state if it broke.

If a module is already well covered by meaningful tests, say so and pick another rather
than padding it.

## If you get blocked

Branch creation, network access, or writes outside the repo may be denied. Denial is
normal — exit cleanly rather than working around it.

**Leave no residue.** Revert any change you could not validate and commit
(`git checkout -- <file>`), delete every scratch file you made, and confirm with
`git status --porcelain` that you left the tree as you found it. Never write to `/tmp` or
outside the repo as a workaround.

Then report what you would have done and which commands need approval. A clean blocked run
is a good outcome; a half-applied edit stranded on `main` is not.

## Deliver

Branch: `coverage/<module-name>`.

Commit message: module, what the tests cover, coverage before → after. End with:

```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

Push and open a PR with `gh pr create`. In the description state:
- the module and why you chose it
- what behaviors the new tests pin down
- **any bug the tests exposed** — the most valuable thing this job can produce
- what remains untested in that module and why

End the PR description with:

```
🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

Append a line to `COVERAGE-BACKFILL.md` recording the module and date, so the next run
picks a different one. Do not merge the PR.
